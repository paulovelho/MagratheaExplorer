# Migrating an instance to 1.5.0

1.5.0 isn't a pull plus a migration. It adds a Python program that makes every thumbnail, a
cron line that has to run every minute, two required PHP extensions, and it changes how key
secrets are stored in a way that can't be undone. Read this page to the end before starting,
including [Not verified yet](#not-verified-yet).

Follow the steps in order. [docs/deploy.md](deploy.md) has the detail behind each one, and
[api/changelog.md](../api/changelog.md) lists every change.

Three things bite if you skip them:

1. **No processor, no thumbnails.** Since 1.5.0, PHP makes no thumbnail at all. Without a
   working `processor_command`, every new image gets `processing.status: "none"` and
   `thumbnail_url: null`. Old thumbnails keep working. ([step 7](#7-image-processor))
2. **Key secrets become one-way hashes.** After the migration, nobody can read a key's secret
   again, the admin included. The dump you take first is the only way back.
   ([step 1](#1-before-the-day), [step 3](#3-back-up))
3. **The API breaks for some clients.** Datetimes switch to UTC, boolean flags parse strictly,
   and thumbnails can arrive late. ([step 2](#2-check-the-consumers))

---

## 1. Before the day

- **The instance must be on 1.4.0**, with `1.4.0_magrathea3.sql` applied: `cat api/version`
  says `1.4.0`, and `cd api && vendor/bin/magrathea models:verify` shows no ERROR. Coming from
  1.3.x, do [Upgrading to 1.4.0](deploy.md#upgrading-to-140-magratheaphp-3) first, separately.
- **Save every key secret you still need.** Today the admin's key form shows a key's secret.
  After the migration it never will. Make sure every integration (social, users of the explorer
  app, any script) has its secret stored on its own side. A secret lost after the migration can
  only be rotated, and the integration then has to be updated.
- **Disable keys held by anyone you don't fully trust,** until 1.5.0 is live. 1.4.x has an SVG
  upload hole that lets any key holder read files on the server, `configs/` included. 1.5.0
  closes it (changelog, first entry).
- **Server requirements** (check the **web** PHP, not only `php -m`: on shared hosts the CLI is
  often another build; [dreamhost-tests.md §4](dreamhost-tests.md#4-check-the-web-php) has a
  check page):
  - PHP extensions `mbstring` and **`xmlreader`**, both required now. Without `xmlreader`, every
    SVG upload fails with a 500.
  - `proc_open` allowed (not in `disable_functions`), for the web PHP **and** the CLI: small
    images are processed during the upload request, big ones from cron.
  - Python 3 with `venv` (3.12 and 3.13 were tested). Nothing else: the pyvips wheel carries its
    own libvips.
  - Only if you'll turn on uploads from a URL: `curl` (and `intl` for international host names),
    and outbound HTTPS from the web PHP.
  - Disk in `processing_tmp_path` (default `api/tmp`, inside the account): the processor's job
    folders, plus, on S3/R2, about twice the size of each object fetched back (half of it in the
    system temp dir).
- **Rehearse the migration on a copy.** Load the latest dump into a scratch database, apply
  `1.5.0_pipeline.sql` to it ([step 4](#4-update-the-code-and-migrate-back-to-back)), and check
  that a secret you know still matches a key:

  ```sql
  SELECT id, name FROM access_keys WHERE secret_hash = SHA2(LOWER(TRIM('<a key secret>')), 256);
  ```

  One row means the hashing works for real data. Part 2 of the migration has never run on
  anything but this rehearsal ([Not verified yet](#not-verified-yet)), so don't skip it.

## 2. Check the consumers

What 1.5.0 changes for API clients, and who is affected as far as the code in `~/www` shows
(checked 2026-11-19). Third parties working from the published skill guide are unknown.

| Change | Affects | What to do |
|---|---|---|
| Every datetime is ISO 8601 UTC: `2026-11-17T06:22:10Z` (was local time with no offset). Same field names, still `/api/v1` | Clients that parse `Y-m-d H:i:s`, or add the server's offset themselves | Parse ISO 8601. The explorer app already does. social stores `created_at` and never reads it |
| `no_convert` (and every new flag) is a strict boolean: `0 false no off ""` are false, garbage is 4009 | Clients that send `no_convert=false` and relied on it meaning true | social sends `"1"`: unaffected |
| Thumbnails come from the processor. Images above 16 MB or 40 MP get `thumbnail_url: null` in the upload response and get it a minute or two later, from cron | Clients that read `thumbnail_url` only from the upload response | **social does exactly that**: an image over 16 MB will never have a thumbnail there. Keep social's key limit at 16 MB or lower, or make social poll `GET /file/{uuid}` (or `POST /files/lookup`) |
| Non-verbatim images above 25 MB or 40 MP are refused with 4131 (413) | Clients that upload big images without `verbatim=1` | social uploads with `no_convert=1`, not verbatim: affected only if its key allows more than 25 MB |
| The default thumbnail is center-cropped (portraits were cropped from the top), and a transparent image's jpg thumbnail is white where it was black. A BMP stored as BMP gets none | New uploads only | Nothing, unless a client compares pixels |
| Key secrets are shown once, never readable again | The operator | [Step 1](#1-before-the-day) |
| JSON bodies: `application/json; charset=…` and `+json` now parse as JSON; `text/json` and `application/x-json` are now read as forms; invalid JSON is 40010; a non-upload body over 1 MB is 413; a non-multipart `POST /files` is 4001, not 4002 | Clients with unusual content types | None found |
| `/changelog` also returns `breaking`, `db` and `upgrade` entries | Clients with a strict `type` enum | None found |

Turbopod is new and is written against 1.5.0.

## 3. Back up

From `api/`, right before the migration:

```sh
cd /var/www/explorer/api && vendor/bin/magrathea db:dump before-1.5.0
```

This dump holds **every key secret in plaintext**: it's the only way to roll back, and it's
also a liability. Keep it out of shared and public places, and delete it once 1.5.0 has settled
([step 12](#12-once-it-has-settled)).

The migration doesn't touch storage objects, so storage needs no backup.

## 4. Update the code and migrate, back to back

From the `git pull` until the migration finishes, **the API and the admin are down**, and
migrating before pulling doesn't help: 1.5.0 code looks keys up by `secret_hash`, which 1.4.0's
schema lacks, and 1.4.0 code needs `access_keys.uuid`, which the migration drops. So run the
block below in one go, off-peak, and not at 3:00 when `cron.php --run` fires.

```sh
cd /var/www/explorer
git pull --ff-only
(cd api && composer install --no-dev --optimize-autoloader)
mysql -h <db_host> -u <db_user> -p <db_name> < api/database/migrations/1.5.0_pipeline.sql
```

- `composer.json` didn't change in 1.5.0. `composer install` is just the usual step.
- `1.5.0_pipeline.sql` holds every schema change of 1.5.0, in three parts. Two of its ALTERs
  rebuild a whole table (`files`, and `folders` on older MySQL versions), and writes to that
  table wait meanwhile. On a large instance that takes a while.
- **It can't be rolled back and can't be re-run.** MySQL/MariaDB commit each ALTER on its own,
  and a second run fails on the first `ADD COLUMN`. If any statement fails: restore
  `before-1.5.0`, fix the cause, and run the whole file again.
- Every existing key keeps working with the secret it has, upper case included. Every existing
  thumbnail becomes a `thumb` rendition, with the same object, token and URL. Its
  `width`/`height`/`size` stay null until it's regenerated.

## 5. Check the schema, clear the cache

```sh
cd /var/www/explorer/api && vendor/bin/magrathea check && vendor/bin/magrathea models:verify
```

Both must report no ERROR. An INFO about `files.thumbnail_token`/`thumbnail_path` is expected:
the columns stay for a rollback, and the model no longer reads them.

Two quick counts. The first must equal the second:

```sql
SELECT COUNT(*) FROM file_renditions;
SELECT COUNT(*) FROM files WHERE thumbnail_token IS NOT NULL AND thumbnail_path IS NOT NULL;
```

Then empty the API cache, which holds the old `/error-codes` and `/changelog`: delete
`cache_path/*.json` (`api/cache/` by default), or use the admin's Cache page.

## 6. Runtime folder and configuration

`processing_tmp_path` (default `api/tmp`) has to exist and be writable by `WEB_USER`. It holds
cron's lock files, the processor's job folders and `source_url` downloads. The simplest way is
to rerun the installer. On an existing instance it's safe: it never overwrites configs, and it
doesn't load the schema into a database that has tables.

```sh
WEB_USER=www-data scripts/deploy.sh install     # DreamHost: WEB_USER=$USER
```

Its "Check PHP requirements" step now checks `mbstring` and `xmlreader` too (the CLI's).
"Create runtime directories" creates the folder. "Check the image processor" belongs to
[step 7](#7-image-processor).

New keys in the environment section of `magrathea.conf` (all are in
`api/configs/magrathea.conf.sample`):

| Key | Default | Set it? |
|---|---|---|
| `processor_command` | none | **Yes**, [step 7](#7-image-processor) |
| `processing_tmp_path` | `api/tmp` | Only to move it. Keep it inside the account, not the shared `/tmp` |
| `client_ip_header` | none (`REMOTE_ADDR`) | **Behind Cloudflare, if a project provisions keys:** `CF-Connecting-IP`. Otherwise one attacker's failed attempts lock every client out of `POST /provision/keys` (rate limit per IP). Only when the origin is reachable through the proxy alone |
| `source_url_enabled` | `false` | Only where a consuming project needs uploads from a URL ([deploy.md](deploy.md#uploads-from-a-url)) |
| `source_url_timeout_s`, `source_url_ports` | `90`, 443 only | Keep the timeout under 100 s behind Cloudflare |
| `verbatim_default` | `false` | Leave it. Set verbatim per key in the admin |
| `convert_max_bytes`, `convert_max_pixels` | `25M`, `40000000` | Only together with `memory_limit` |
| `processor_timeout_s`, `processor_memory_mb`, `max_pixels` | `120`, `384`, `200000000` | Measured defaults. Change `max_pixels` and `processor_memory_mb` together, then rerun run-fixtures |
| `inline_max_bytes`, `inline_max_pixels` | `16M`, `40000000` | Leave them |
| `cron_process_max_files`, `cron_process_max_s`, `processing_max_attempts` | `20`, `50`, `3` | Keep `cron_process_max_s` under the cron interval |
| `idempotency_retention_h` | `24` | 24 at least, or `--process` fails with 5004 |
| `folder_delete_inline_files`, `folder_delete_max_s` | `200`, `15` | Leave them |

A value these keys can't read is a 5004 naming the key, except the processing keys, which never
fail an upload: images are stored with `processing.status: "failed"` and an error naming the
key.

**Don't touch `timezone`.** It's the zone the stored times are in, and the API now converts
from it to UTC. Changing it on an instance with data shifts every stored time.

**Anyone who can log into the admin can now run commands as `WEB_USER`:** the admin's Setup →
Configuration File page writes `magrathea.conf`, `processor_command` included. Treat admin
accounts as shell accounts.

## 7. Image processor

On DreamHost, follow [dreamhost-tests.md](dreamhost-tests.md) instead of this section: it covers
the same steps, plus the web PHP and cron checks.

1. Build the venv as `WEB_USER`, outside the repo:

   ```sh
   python3 -m venv ~/explorer-venv
   ~/explorer-venv/bin/pip install -r /var/www/explorer/api/processor/vips/requirements.txt
   ```

2. Point `magrathea.conf` at it, as a JSON argv, single-quoted, with absolute paths:

   ```ini
   	processor_command = '["/home/u/explorer-venv/bin/python","/var/www/explorer/api/processor/vips/processor.py"]'
   ```

3. Run the contract fixtures as `WEB_USER`. Every check must pass:

   ```sh
   php /var/www/explorer/api/processor/run-fixtures.php
   ```

   `scripts/deploy.sh install` runs the same check (step 8, as `WEB_USER`).

If the system Python is ever upgraded, the venv breaks and every image ends up `failed` with a
Python error. Rerun run-fixtures after every deploy and every server change. The fix is
`rm -rf ~/explorer-venv` and step 1 again.

The dev Docker image has no Python, so dev makes no thumbnails at all (decided: no Docker
changes for now).

## 8. PHP limits (only for keys above 64 MB)

Keys can now have their own upload limit (admin → Keys, "Max upload (MB)"), but PHP's limits cap
every key. For keys up to 150 MB, `api/src/.user.ini`:

```ini
upload_max_filesize=160M
post_max_size=170M
max_input_time=300
max_execution_time=300
memory_limit=512M
```

`memory_limit` stays at 512M: uploads stream. What sits in front of PHP has its own body limit.
On Cloudflare's Free and Pro plans, a proxied API hostname stops at 100 MB: make it DNS-only, or
keep key limits under 100 MB. That matters most for direct browser uploads of print files.
Details: [deploy.md, Large uploads](deploy.md#large-uploads-per-key-limits).

## 9. Cron

As `WEB_USER`:

```cron
* * * * * php /var/www/explorer/api/src/cron.php --process >> /var/www/explorer/api/logs/cron.log 2>&1
0 3 * * * php /var/www/explorer/api/src/cron.php --run >> /var/www/explorer/api/logs/cron.log 2>&1
```

- **`--process` is new and required.** It makes the renditions of big images and bulk imports
  (without it they stay `pending` forever), retries failed processing, retries failed storage
  deletes, sweeps recursive folder deletes, and purges rate-limit counts, Idempotency-Key
  records, upload tokens and old job folders. A run that finds the previous one still going exits
  at once.
- **`--run` is now required wherever keys are provisioned:** it's what carries out
  `DELETE /key` 14 days later. **The DreamHost instance has no `--run` line** (found 2026-11-17):
  add it.
- Files from before 1.5.0 have `sha256: null`. Fill them in once, then remove the line. On a host
  that kills long processes, cap each run:

  ```cron
  */10 * * * * php /var/www/explorer/api/src/cron.php --backfill-sha256 --max-seconds=240 >> /var/www/explorer/api/logs/cron.log 2>&1
  ```

  It's done when a run's summary says `0 still without a hash`.

## 10. Admin

- **Keys:** each key has new settings: "Images without verbatim flag", "Max upload (MB)" and
  "Renditions" (a JSON profile, with a thumb 300 + preview 1200 preset). Empty means the
  instance default. The key list is paged, and filters admin-made from provisioned keys.
- **Provisioning:** only for a project that creates its own keys (Turbopod). Set *Max keys* and
  the settings each key gets first, then **Generate secret**. It's shown once.
- **Processing:** the queue, recent failures, storage deletes that keep failing, and whether the
  processor is configured. Look at it after the first uploads.

Regenerating old thumbnails is optional (`cron.php --regenerate --key=<id>`, the Browser's
"regenerate", or `POST /file/{uuid}/renditions`). **It gives every image new rendition URLs and
deletes the old objects.** Don't regenerate a key whose consumer stores thumbnail URLs or paths
and never re-reads them, and social does exactly that. `POST /file/{uuid}/rotate` has the same
effect on the file's own URL.

## 11. Smoke test

- `curl https://<host>/api/v1/version` says `1.5.0`.
- An **existing** key works with its old secret: `GET /key` answers 200, its `created_at` ends
  in `Z`, and it has `max_upload_size` and `rendition_profile`.
- A thumbnail URL from before the upgrade still loads.
- A small PNG upload with an existing key: the response has `sha256`, `properties`,
  `processing.status: "ready"`, and a `thumbnail_url` that loads.
- An SVG upload works (proves `xmlreader` in the web PHP).
- If any key allows it, an image over 16 MB: `pending` first, `ready` within a couple of minutes
  (proves the `--process` cron line).
- admin → Processing says the processor is configured, with no failures.

## 12. Once it has settled

- **Delete `before-1.5.0` and every older dump**, offsite copies included: they hold every key
  secret in plaintext.
- **Look for exploitation of the old SVG hole.** An attempt keeps its DOCTYPE, so any stored
  `.svg` containing `<!ENTITY` is one:

  ```sh
  # local storage
  grep -rl --include='*.svg' '<!ENTITY' <local_path>
  # R2/S3, with rclone
  rclone lsf -R --files-only --include '*.svg' r2:<bucket> | while read -r f; do
    rclone cat "r2:<bucket>/$f" | grep -q '<!ENTITY' && echo "$f"; done
  ```

  If anything turns up, rotate the database password and the storage keys.
- Remove the `--backfill-sha256` cron line once it's done.
- Re-enable the keys you disabled in [step 1](#1-before-the-day).

## Rolling back

The only way back is the dump: restore `before-1.5.0`, check out 1.4.0, `composer install`,
clear the cache. What that costs:

- Everything written since the migration is gone from the database: files uploaded since then
  (their objects stay in storage as orphans, renditions included), keys created or rotated, and
  settings changed.
- Thumbnails from before 1.5.0 keep working (`thumbnail_token`/`thumbnail_path` were kept for
  this), **except** on files that were regenerated or rotated in 1.5.0: those operations deleted
  the old thumbnail objects.
- The SVG hole is open again.

## Not verified yet

Read this before migrating a production instance. None of it has failed. None of it has run
either.

1. **The migration has never run on a real database.** Part 1 ran on a throwaway MariaDB 11
   loaded with the 1.4.0 schema. Parts 2 and 3 have never run anywhere, `models:verify` included.
   Part 2 is the one-way secret hashing. Hence the rehearsal in [step 1](#1-before-the-day).
2. **No DB-backed integration check has run** for Tiers 2 and 3, and Tier 1's has gaps. The
   lists are in `.claude/plan-1.5.0-tier1.md` §10, `plan-1.5.0-tier2.md` §9 and
   `plan-1.5.0-tier3.md` §9 / §8.1. The riskiest:
   - every existing key authenticates after the hashing, and rotation kills the old secret;
   - Idempotency-Key under concurrency (409 while running, a replay after success, 422 for a
     different request);
   - the recursive-delete sweep's self-joined `UPDATE folders … INNER JOIN folders …` on the
     production MySQL/MariaDB version;
   - two `POST /upload/{token}` at once: one 200, one 4092.
3. **S3/R2 has never been exercised** for any 1.5.0 storage call: `fetch()` (backfill, queue),
   the rendition `put()`s, `copy()` (rotation must keep Content-Type, Content-Disposition and
   Cache-Control).
4. **DreamHost:** run-fixtures on the server; `proc_open`, `XMLReader` and `curl` in the web
   PHP; whether every-minute cron is allowed; a 150 MB upload through the front proxy; a 150 MB
   `source_url` fetch, to find the FastCGI timeout; DNS timing
   ([dreamhost-tests.md](dreamhost-tests.md) steps 3–6).
5. **The verbatim acceptance test:** upload a 16-bit RGBA PNG with ICC and pHYs
   (`api/processor/fixtures/rgba16-icc-phys300.png`) with `verbatim=1`, download its `url`, and
   compare `sha256sum`. Do it on both storage drivers.
6. **Release housekeeping:** the changelog's 1.5.0 date still says `unreleased`. Send Turbopod
   the final `docs/openapi.yaml`, `docs/skills.md` and `/error-codes`.
7. **Framework follow-ups**, not blocking: Explorer works around each one. MagratheaPHP's JSON
   media-type detection, its local-time `HealthCheck()`, `GetPagination()` skipping a row without
   a total, its Configuration File page accepting new keys, and DB error details in API error
   responses.
