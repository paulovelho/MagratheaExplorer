# Credentials feature — implementation plan

Written against `master` @ `6e9c6e0` (`api/version` = 1.3.0). Nothing below is implemented yet.
Target version: **1.4.0**.

## Why

Today `access_keys.uuid` is both the tenant's identity and its only credential:

- stored and displayed in **plaintext** (`database.sql:53`, `Key/admin/form.php:28`);
- **cannot be rotated** (`KeyControl::UpdateFields()` deliberately never touches it) — a leak
  means deactivating the whole tenant;
- **one per tenant** — every service that talks to a key shares the same secret, so you can't
  tell them apart or revoke one;
- **all-powerful** — whoever holds it can list everything, delete every file/folder, create
  public share links to the root folder, and `DELETE /key`.

The stated concern is exactly the last point: *someone getting the full list of files and being
able to delete it all.* Hashing and rotation alone don't stop that — so this plan puts
**scopes** on every credential. An upload-only service gets a credential that can't list or
delete anything.

## What it does

- A key (tenant) can have **many credentials**. Each has a name ("billing-service"), a set of
  **scopes**, an optional **expiration**, and can be **revoked** individually.
- The secret looks like `mxk_` + 43 base62 chars (~256 bits). Only its **SHA-256** is stored.
  The full secret is shown **once**, on creation, in the admin panel. Afterwards only the
  prefix (`mxk_Ab3dE6gH`) is shown.
- Each credential records `last_used_at` / `last_used_ip`.
- Every existing key keeps working **with no client change**: the migration turns each
  `access_keys.uuid` into a full-scope credential named `legacy`, then drops the plaintext
  column.
- Credentials are created and revoked **only in the admin panel** — same rule as key creation
  today (no public endpoint).
- Files themselves stay served by the public storage URLs, same as now (out of scope, by choice).

## 1. Gotchas verified in this codebase

### 1.1 Route auth can call any method — scopes can be declarative per route

`MagratheaApi::Add($method, $url, $control, $fn, $auth)` stores `$auth` as a method name, and
`Run()` calls `$this->authClass->$auth($params)` (`MagratheaApi.php:465`). So instead of one
`IsAuthenticated`, `KeyAuthControl` can expose `CanRead`, `CanWrite`, … and each route in
`api.php` names the one it needs. An exception thrown there is caught by `Run()` and returned
as that exception's error; a plain `false` becomes a generic 401.

### 1.2 Only the URL is lowercased, not headers

`MagratheaApi::Run()` lowercases the URL (see `plan_share.md` §1.1). Base62 secrets are
case-sensitive, so **a secret must never be put in a URL** — header only. That's already the
rule for the key uuid; it just matters more now.

### 1.3 `uuid`-typed fields are auto-minted on `Insert()`

`MagratheaModel::CreateInsertQuery()` fills every `"uuid"`-typed `dbValues` entry with
`Uuid::V7()` when it's empty. The credential secret must **not** be a `uuid` field — it's
generated by our own code and never stored. When `access_keys.uuid` is dropped, its
`dbValues` line and property in `KeyBase` must be removed too, or `Insert()` will write to a
column that no longer exists.

### 1.4 No FK is `ON DELETE CASCADE`

`KeyControl::DeleteKeyNow()` must delete `key_credentials` rows before `$key->Delete()`.

### 1.5 The Vue app logs in *with* the secret

`LoginView.vue` saves whatever the user types to `localStorage` and sends it as
`Bearer …` (`api/client.js:34`). Legacy key uuids keep working thanks to the backfill. New
secrets work the same way — the app doesn't care about the format. A browser login should
still use a **separate** credential from any server-side service, so revoking one doesn't
break the other.

### 1.6 The app only clears its login on 401

`client.js` clears the stored key and redirects on 401, but not on 403. So a scope failure
(403) leaves the user logged in. That's the behavior we want; the UI just needs to hide
actions the credential can't perform (§6).

### 1.7 Unknown key currently returns 404, not 401

`ResolveFromBearer()` throws 4041 ("Key not found") for an unknown bearer, and the route gate
turns any failure into a bare 401 anyway. It's inconsistent and it tells a caller whether a key
exists. After this change: an unknown, revoked or expired **credential** is always **4011 / 401**.
`4012`/`4013` (key expired / inactive) are only reachable with a valid secret, so they give
nothing away.

## 2. Scopes

Five coarse scopes, stored as a comma-separated `varchar`. They are independent — `write` does
**not** imply `read`.

| Scope    | Routes |
|----------|--------|
| *(any valid credential)* | `GET key` — the caller's own key and credential info only |
| `read`   | `GET key/usage`, `GET folders`, `GET folder/:uuid`, `GET folder/:uuid/size`, `GET files`, `GET file/:uuid`, `GET shares` |
| `write`  | `POST folders`, `PUT folder/:uuid`, `POST files`, `PUT file/:uuid`, `POST file/:uuid/tags`, `DELETE file/:uuid/tags/:tag` |
| `delete` | `DELETE file/:uuid`, `DELETE folder/:uuid` |
| `share`  | `POST shares`, `DELETE share/:uuid` |
| `manage` | `DELETE key`, `POST key/cancel-deletion` |

Notes:
- **`share` is as powerful as `read`**: a share link on the root folder publishes everything.
  Grant it only where `read` is also acceptable.
- **`write` without `read`** can upload (to the root folder, or to a `folder_uuid` given to the
  service ahead of time) and gets back the uploaded file's own view, but can't list anything.
  This is the "upload-only external service" profile.
- `GET key` needs **no scope**, only a valid credential. The app uses it at login and on every
  page load to learn what the credential may do (§6), and it only describes the caller itself.
  It now also returns the calling credential's `name`, `prefix`, `scopes` and `expiration`.
- Suggested presets in the admin form: **Upload only** (`write`), **Read only** (`read`),
  **App login** (`read,write,delete,share`), **Full** (all five). `manage` is never checked by default.

## 3. Database

### 3.1 New table `key_credentials`

```sql
CREATE TABLE `key_credentials` (
	`id` int(11) PRIMARY KEY AUTO_INCREMENT,
	`key_id` int(11) NOT NULL,
	`name` varchar(255) NOT NULL,
	`prefix` varchar(16) NOT NULL COMMENT 'First chars of the secret, for display only. Not secret, not unique.',
	`secret_hash` char(64) NOT NULL UNIQUE COMMENT 'hex SHA-256 of the full secret. The secret itself is never stored.',
	`scopes` varchar(255) NOT NULL COMMENT 'Comma-separated: read,write,delete,share,manage',
	`expiration` datetime NULL,
	`revoked_at` datetime NULL,
	`last_used_at` datetime NULL,
	`last_used_ip` varchar(45) NULL,
	`created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
	`updated_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
	KEY `idx_credentials_key` (`key_id`),
	UNIQUE KEY `uq_credential_name` (`key_id`, `name`),
	FOREIGN KEY (`key_id`) REFERENCES `access_keys`(`id`)
);
```

A fast hash (SHA-256) is fine here: the secret has 256 bits of entropy, so there's nothing to
brute-force offline. bcrypt/argon2 would only add latency to every request.

### 3.2 Migrations — two files, run around the deploy

**`migrations/1.4.0_credentials.sql`** — run **before** deploying the 1.4.0 code. Additive only;
the old 1.3.0 code keeps working after it.

```sql
CREATE TABLE `key_credentials` ( ... as above ... );

-- Every existing key's uuid becomes a full-scope credential. The hash of the exact string
-- clients already send, so no client needs to change.
INSERT INTO `key_credentials` (`key_id`, `name`, `prefix`, `secret_hash`, `scopes`, `created_at`)
SELECT `id`, 'legacy', LEFT(`uuid`, 8), SHA2(`uuid`, 256), 'read,write,delete,share,manage', `created_at`
FROM `access_keys`;
```

MySQL `SHA2(x, 256)` returns lowercase hex, which matches PHP `hash("sha256", $x)`. The
blueprint step must check that on the real DB (one `SELECT` comparing the two for one row).

**`migrations/1.4.0_drop_key_uuid.sql`** — run **after** 1.4.0 is deployed and a legacy client
has been seen to authenticate.

```sql
-- Irreversible: this is the last plaintext copy of every legacy secret. Back up first if a
-- rollback to 1.3.0 must stay possible.
ALTER TABLE `access_keys` DROP COLUMN `uuid`;
```

Don't create keys between the first migration and the deploy: 1.3.0 would mint a uuid with no
matching credential. (If it happens, just re-run the `INSERT … SELECT` restricted to keys that
have no credential.)

### 3.3 `database.sql` (fresh install)

Add `key_credentials`, remove `uuid` from `access_keys`.

## 4. API

### 4.1 New files under `features/Key/`

Same layout as `ScheduledDeletion`, which already lives under the Key feature:

- `Base/CredentialBase.php`, `Base/CredentialControlBase.php` — generated-style, table
  `key_credentials`. Also add a `[credential]` section and a `Credential <-> Key` relation to
  `configs/magrathea_objects.conf`, so regenerating through the admin doesn't drop it.
- `Credential.php`
  - `SCOPES = ["read", "write", "delete", "share", "manage"]`
  - `Scopes(): array`, `HasScope(string): bool`
  - `AssertUsable()`: throws 4011 if revoked or expired (same code as an unknown secret, see §1.7)
  - `TouchUsage()`: a single throttled write —
    `UPDATE key_credentials SET last_used_at = NOW(), last_used_ip = ? WHERE id = ? AND (last_used_at IS NULL OR last_used_at < NOW() - INTERVAL 1 MINUTE)`
    so a burst of requests doesn't write on every call.
- `CredentialControl.php`
  - `Create(Key $key, string $name, array $scopes, ?string $expiration): array` — returns
    `[Credential, string $secret]`. The secret leaves this function exactly once and is never
    logged. Rejects unknown scopes and an empty scope list.
  - `Revoke(Credential)` — sets `revoked_at`. The row is kept for audit.
  - `ResolveFromBearer(?string $secret): Credential` — `hash("sha256", …)`, then look up by
    `secret_hash`, then `AssertUsable()`, then load the key and call `Key::AssertUsable()`.
    Missing, unknown, revoked or expired → **4011**.
  - `DeleteForKey(int $keyId)`.
- `SecretGenerator` — or generalize `File\TokenGenerator::Generate()` to take a length and
  reuse it: `"mxk_" . Generate(43)`. The prefix is the first 12 chars (`mxk_` + 8).

### 4.2 Changes

- **`KeyControl::ResolveFromBearer()`** → removed. Callers use `CredentialControl::ResolveFromBearer()`
  and then `->GetKey()`.
- **`KeyControl::DeleteKeyNow()`** → call `CredentialControl::DeleteForKey()` before `$key->Delete()`.
- **`KeyAuthControl`**:
  ```php
  public function IsAuthenticated(): bool { return $this->Authorize(null); }   // GET key only
  public function CanRead(): bool   { return $this->Authorize("read"); }
  public function CanWrite(): bool  { return $this->Authorize("write"); }
  public function CanDelete(): bool { return $this->Authorize("delete"); }
  public function CanShare(): bool  { return $this->Authorize("share"); }
  public function CanManage(): bool { return $this->Authorize("manage"); }

  private function Authorize(?string $scope): bool {
  	try {
  		$credential = CredentialControl::ResolveFromBearer($this->GetAuthorizationToken());
  	} catch(\Throwable $ex) {
  		return false;                                   // -> generic 401
  	}
  	if($scope !== null && !$credential->HasScope($scope)) {
  		ErrorCodes::Instance()->ThrowException(4033, null, $scope);   // -> 403
  	}
  	$credential->TouchUsage();
  	return true;
  }
  ```
  `IsAuthenticated` stays, but now means "any valid credential, no scope needed" and is used by
  `GET key` only. `BaseAuthorization()`'s default stays `IsAuthenticated`, but no other route
  should rely on it (see the grep check below).
- **`ExplorerApiControl`**: add `GetRequestCredential(): Credential`. `GetRequestKey()` becomes
  `GetRequestCredential()->GetKey()` (cached, as now). This is still a second lookup — the route
  gate and the controller are different instances (see the existing docblock) — and it's still
  cheap: one unique-index lookup.
- **`api.php`**: replace `self::AUTHENTICATED` on every route with the scope constant from the
  table in §2 (`const READ = "CanRead"`, etc.). Every route must name exactly one scope, except
  `GET key`, which keeps `AUTHENTICATED`. The blueprint should include a grep check that
  `AUTHENTICATED` appears on that route only.
- **`KeyApi::GetSelf()`**: add a `credential` object to the response: `{ name, prefix, scopes, expiration }`.
  Never the hash.
- **`KeyBase`**: remove `$uuid` from the properties and from `dbValues`. `Key::Normalize()`'s
  docblock mentions `uuid` — update it.
- **`error_codes.conf`**:
  - `4011` → `"Missing or invalid credential"`
  - new `4033 = "Credential lacks the required scope"`
  - `4041` stays in the file but is no longer thrown by auth.

### 4.3 Not doing

- **Public credential-management API.** Admin panel only, same as keys. It could come later
  behind the `manage` scope.
- **Rate-limiting failed attempts.** A 256-bit secret can't be guessed online, so there's
  nothing for rate-limiting to protect. Logging failures (Logger API) would be cheap if wanted
  later.
- **IP allowlists and per-folder scopes.** Not needed for the stated threat; the table has room to
  add columns later.
- **Signed file URLs.** Excluded by choice.

## 5. Admin panel

Everything goes on the existing **Edit Key** page (`Key/admin/form.php`). No new menu item.

- **Remove** the `UUID` field. Keep `Storage dir (public)`.
- New **Credentials** card below the key form:
  - Table: name, prefix (`mxk_Ab3dE6gH…`), scopes, created, last used (+ IP), expiration,
    status (active / expired / revoked), and a **Revoke** button (POST + CSRF, `confirm()`).
  - **New credential** form: name, scope checkboxes with the presets from §2, optional
    expiration.
- New `KeyAdmin` actions:
  - `CreateCredential()` (POST) — creates the credential and renders a **"copy this now"** page
    showing the full secret, with a warning that it won't be shown again. This action must

    a "Done" link back to the key.

- **New Key flow**: after `Save()` creates a key, redirect to its Edit page (not the list) so the
  operator creates the first credential right away. A new key has **no** credentials until then.
- **Keys list** (`admin/list.php`): add a "Credentials" column showing the active count.

## 6. App (Vue)

### 6.1 How login works

The flow the user sees is the same as today. What changes is where the secret comes from.

1. An operator creates a credential in the admin panel (Keys → Edit key → New credential),
   using the **App login** preset (`read,write,delete,share`, never `manage`). Name it after the
   person or device (`paulo-laptop`), and set an expiration if wanted.
2. The admin panel shows the `mxk_…` secret once. The operator copies it and gives it to the person.
3. The person pastes it on the login screen. The app calls `GET /key`, stores the secret, loads
   the scopes (§6.2) and opens the explorer.
4. **One credential per person or device.** A lost laptop means revoking one credential,
   not everyone's.
5. Revoking takes effect on the next request: 401, the app clears its storage and goes back to login.

Existing logins keep working: the old key uuid already in `localStorage` matches its `legacy`
credential.

**Login screen changes (`LoginView.vue`, `client.js`):**
- The input becomes `type="password"` with `autocomplete="off"`. Today it's `type="text"`, so
  the secret shows on screen and may be saved by the browser.
- A **"Remember this device"** checkbox. Unchecked (the default) → the secret goes in
  `sessionStorage` and is gone when the tab closes. Checked → `localStorage`, as today.
  `getKey()` reads `sessionStorage` first, then `localStorage`. `clearKey()` clears both.
- Never accept the secret from the URL (`?key=…`): URLs end up in history and server logs, and
  `MagratheaApi::Run()` lowercases them (§1.2), which would break a base62 secret.
- On 401: "Invalid, expired or revoked key."
- **A credential without `read` is blocked at login.** `GET /key` succeeds, but if `scopes`
  doesn't include `read`, the app clears the key and shows: "This key can't browse files. It's
  meant for a service, not for this app." (An upload-only mode for such credentials is listed
  under §10.)

### 6.2 Knowing the scopes on every page load

Today `fetchKey()` runs only at login. After a refresh, the router guard just checks that
`localStorage` has a key, so the app wouldn't know its scopes.

- New module-level composable `composables/useCredential.js`, following the same pattern as
  `useKeyUsage.js`:
  `credential` (`{ name, prefix, scopes, expiration }`), `can(scope)`, `ensureLoaded()`, `reset()`.
- `ensureLoaded()` calls `GET /key` once and keeps the pending promise, so concurrent callers
  share one request.
- `router.beforeEach`: for any non-public route with a key present, `await ensureLoaded()`. A 401
  in there → `clearKey()` + redirect to login.
- `reset()` is called on logout (`AppHeader.logout()`) and on 401 (`client.js`), alongside
  `clearKey()`. Otherwise logging in with a different credential would briefly show the previous
  one's buttons.
- The `shares` route gets `meta: { scope: 'read' }`. The guard redirects to the explorer if
  `!can(to.meta.scope)`.

### 6.3 Hide what the credential can't do

Hide these controls rather than disabling them: disabled buttons on every row are clutter, and
the badge (§6.4) explains why they're missing.

| Where | Shown when |
|---|---|
| `UploadZone`, **New folder** button (`ExplorerView`) | `can('write')` |
| Rename in `FileList` rows (folders and files) | `can('write')` |
| Delete in `FileList` rows | `can('delete')` |
| Share in `FileList` rows | `can('share')` |
| **Shared links** nav in `AppHeader` | `can('read')` (it's a list); the delete button in `SharesView` needs `can('share')` |
| Usage label in `AppHeader` | `can('read')` (`GET key/usage`) |

`FileList` receives `canWrite` / `canDelete` / `canShare` **props** from `ExplorerView`, rather
than calling the composable itself. It's a presentational component that only emits events today,
and that keeps it that way.

### 6.4 Show which credential is in use

- `AppHeader` shows a small badge: `{credential.name} · {summary}`, e.g. "phone · full access",
  "billing-app · read only". Summary: all four app scopes → "full access"; only `read` →
  "read only"; otherwise the list of scopes. Hover (or tap on mobile) shows the full list and the
  prefix.
- If `expiration` is within 7 days, show a banner above the breadcrumbs:
  "This access key expires on {date}."

### 6.5 Errors

- `client.js`: on 403 with code `4033`, the error message becomes "This access key isn't allowed
  to do that." It goes into the view's existing `errorMessage` banner. **Don't log out.** If
  §6.3 hides the right controls this should rarely happen; it's a fallback.
- 401 behavior is unchanged (clear + back to login), plus `reset()` from §6.2.

## 9. Manual test checklist

- Legacy: before step 7's migration, the old key uuid logs into the app and `curl GET /key` works.
  After it, the same still works.
- Create an **Upload only** credential:
  - `POST files` → 200
  - `GET key` → 200 (no scope needed)
  - `GET files`, `GET folders`, `GET key/usage` → 403 / 4033
  - `DELETE file/:uuid`, `DELETE key` → 403 / 4033
  - `POST shares` → 403
- Create a **Read only** credential: listing works; upload, delete and share → 403.
- **App login** credential (no `manage`): the app works fully; `DELETE key` → 403.
- Revoke a credential → its next request gets 401 / 4011, and the app bounces to login. The
  key's other credentials are unaffected.
- Expired credential → 401 / 4011.
- Unknown bearer → 401 / 4011 (not 404).
- Inactive key with a valid credential → 4013, same as today.
- `last_used_at` updates on first use and doesn't update again within a minute.
- Force-deleting a key with credentials → no FK error.
- The secret appears once on the create page and nowhere else: not in the admin log, the
  page source after "Done", the URL history, or the DB.
- `grep -n AUTHENTICATED api/src/api.php` → only the `GET key` route (plus the constant itself).

**App:**
- Logging in with an **Upload only** credential → blocked with the "can't browse files" message;
  nothing left in storage.
- **Read only** login → no upload zone, no New folder, no rename, delete or share in rows.
  **Shared links** is visible, with no delete buttons. The badge says "read only".
- **App login** credential → everything visible, as today. The badge says "full access".
- Refresh the page on `/app/folder/{uuid}` with a read-only credential → the controls are still
  hidden, and there's no flash of hidden buttons appearing first.
- Log out, then log in with a different credential → no buttons left over from the previous one.
- "Remember this device" unchecked → close the tab, reopen `/app` → login screen. Checked → still
  logged in.
- A credential expiring in fewer than 7 days → the expiry banner shows.
- Revoke the credential while the app is open → the next action bounces to login with the
  "revoked" message.
- A forced 403 (e.g. call `deleteFile` from the console with a read-only credential) → message
  shown, still logged in.
- A legacy key uuid in `localStorage` from 1.3.0 → still logged in after the upgrade, with full
  access.

## 10. Later (not in 1.4.0)

### 10.1 Cookie session for the app

The weak spot of §6.1 is a long-lived secret in browser storage: any script running on the page
can read it and use it from anywhere until the credential expires or is revoked. That's acceptable
for a few trusted users with per-device, expiring credentials. If the app is ever opened to less
trusted users, swap the secret for a session once, at login:

1. `POST /auth/login` (open route) takes the secret, resolves it with
   `CredentialControl::ResolveFromBearer()`, and issues a short-lived (e.g. 12h) framework JWT
   holding only `credential_id` and `exp`.
2. The token is set as an **HttpOnly, Secure, SameSite=Strict** cookie with the framework's
   `SetAuthCookie()` (`$cookieName` override on the auth control). The browser never stores the
   secret.
3. `KeyAuthControl::Authorize()` accepts either a `Bearer mxk_…` secret (services) or the cookie
   (the app). For the cookie, it decodes the JWT and **still loads the credential by id** on every
   request, so revocation and scope changes stay instant.
4. `POST /auth/logout` calls `ClearAuthCookie()`. An HttpOnly cookie can't be removed from JS.
5. The app stops using `localStorage`/`sessionStorage` for the key. "Remember this device" becomes
   the cookie's lifetime.
6. Check: `AllowAll()` CORS doesn't combine with credentialed requests, which is fine
   (same-origin app). `SameSite=Strict` is the CSRF defense. Keep it Strict, not Lax, since
   mutating routes include `DELETE`.

Nothing changes for external services.

### 10.2 Upload-only mode ("drop box")

For a credential with `write` but no `read`, instead of blocking it at login (§6.1), the explorer
could show only the upload zone (into the root folder) plus a list of the files uploaded in this
browser session, built from the upload responses since the credential can't list anything. This
is useful for handing someone a "send me files" key. About 40 lines on top of §6. It needs
`ExplorerView` to skip its `fetchFolders`/`fetchFiles` calls when `!can('read')`.

### 10.3 Real user accounts

Because the app always logs in with a credential, email/password (or SSO) accounts could later
simply *issue* credentials or sessions. That wouldn't change the API's auth model.
