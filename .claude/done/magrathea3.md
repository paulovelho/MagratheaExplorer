**DONE (2026-11-17):** plan closed. Committed in `12443dc`.

## 1. Decisions

| Question | Decision |
|---|---|
| Two hops (2.4 first) or one | **One hop**, 2.3.4 → 3.0, applying the 2.4.0 items inline |
| Version | **1.4.0** (but see §6: `plan_credentials.md` also claims 1.4.0) |
| `$strictTypes` (3.0 defaults to `true`) | First pinned `false`, then **dropped (strict)** in the follow-up. API JSON is unchanged either way: no response serializes a model, every one is built in a `…View()` array that already casts ints/bools (`"size":16`, `"active":true` before and after) |
| MySQL session timezone sync (2.4.0 #34) | **Kept on** (3.0 default). Opt-out: `db_sync_timezone = false` in the environment section |
| Inactive admin users (M1) | Not checked: they lose admin access, accepted |
| Downtime during upgrade | Acceptable (a few hours is fine), so no zero-downtime ordering |
| Setup Wizard (M27) | `api/src/setup.php` **deleted**, not replaced by the 3.0 wizard. First-run admin setup is `magrathea.php` (3.0 still has it) |

## 2. What changed (done)

### Framework and bootstrap
- `api/composer.json`: requires `platypustechnology/magratheaphp:^3.0` (2 removed), and
  `extra.magrathea.bootstrap = src/_inc.php` so `vendor/bin/magrathea` finds the bootstrap (M24).
- `Magrathea2` → `Magrathea` in 55 files under `api/src` (M2). `database.sql` header too.
- `api/src/_inc.php`: absolute `require __DIR__."/../vendor/autoload.php"` and `AddRootCodeFolder()`
  (the old relative paths only worked with cwd = `src/`, so the CLI couldn't load it);
  `MinVersion("3.0.0")`; explicit `->Prod()` (same LOG mode as before); `->Connect()`; no more
  `try/catch` + `p_r($ex)` (it printed the exception — config, paths — on the page).
- Entry points log and answer a generic 500 instead of printing: `index.php`, `magrathea.php`
  (+ explicit `StartSession()`), `app-index.php` (bootstrap moved inside its existing fallback).
- Deprecated `StartDb()` removed from `api.php` and `cron.php` (M5).
- `admin/MagratheaExplorerAdmin.php`: `include("api.php")` → `require_once __DIR__."/../api.php"`
  (the CLI loads every class while scanning for models, from another cwd). `index.php` uses
  `require_once` too, so both paths can't declare the class twice.

### Generator leftovers (M3, M6)
- Deleted `api/configs/magrathea_objects.conf`.
- Stripped the `## FILE GENERATED BY MAGRATHEA` header from the 12 `features/*/Base/*.php` and
  dropped deprecated `implements iMagratheaModel` from the 6 Base models (all 12 files were then
  merged away, below).

### Models and API
- `protected $strictTypes = false;` on the 6 Base models (M9), later removed (below).
- `Insert()` no longer fills `created_at` on the object (M10): `->Reload()` added in the three
  create actions that return it — `FileApi::Upload`, `FolderApi::Create`, `ShareApi::Create`.
  Deliberately **not** in `UploadPipeline::Handle()`, which bulk import calls once per file.

### Models (follow-up: Base merge + strict types)
Guide's "Optional: merge Base classes", one feature at a time (Share, Folder, File, Key), each
checked against the baseline before the next (§4).
- `File`, `Tag`, `Folder`, `Key`, `ScheduledDeletion`, `Share` are single classes extending
  `MagratheaModel`: `$dbTable`/`$dbPk`/`$dbValues`/`$relations` as property defaults, no
  constructor, no `GetControl()` (the default resolves `<Model>Control`), no
  `created_at`/`updated_at` in `$dbValues`. All 12 `Base/*.php` and the 4 `Base/` folders deleted.
- Each `<Model>Control` extends `MagratheaModelControl` with `protected static $model = X::class;`.
- The lazyload relation getters are kept (same per-object cache, now `??=`), pointing at the
  concrete Controls. So are the call sites that used `…ControlBase` directly: `TokenGenerator`,
  `PublicShareApi`, `FolderControl::AssertEmpty`, `KeyControl::DeleteKeyNow`/`DeleteFoldersDeepestFirst`,
  `Key::HasPendingScheduledDeletion`.
- `$strictTypes = false` pins removed: loaded models carry native ints/bools. Audited for strict
  comparisons / string assumptions on model fields (none: every view, admin column and
  `DuplicatesAdmin` token already casts).
- Stale comments fixed: 3.0's `Insert()` leaves `null` fields out (column `DEFAULT` applies), not
  "writes every declared field" (`Key::Normalize`, `ShareControl::Create`, `UploadPipeline`);
  `scheduled_deletions` has `created_at` since 1.4.0, so `DeleteKeyNow` uses
  `ScheduledDeletionControl::GetWhere()` instead of the `GetSimpleWhere()` workaround. The
  "regenerating through the admin drops this line" notes went with the Base files.

### Admin (2.4.0 #48)
- New `api/src/shared/AdminPostOnly.php` trait (`RefuseIfNotPost()`: 405 unless POST; protected,
  so the admin router never dispatches it). Applied to the 10 write actions: `KeyAdmin::Save`,
  `ForceDeleteNow`; `ScheduledDeletionAdmin::Cancel`, `ForceExecute`; `ShareAdmin::Delete`;
  `BrowserAdmin::DeleteFile`, `DeleteFolder`, `PurgeOrphan`; `DuplicatesAdmin::DeleteSelected`;
  `ImportAdmin::RunImport`. Before, a plain GET to `KeyAdmin::Save` (no CSRF check on GET)
  created a key.

### Database (M11–M13)
- `api/database/migrations/1.4.0_magrathea3.sql`: adds `created_at`/`updated_at`
  (`DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`, `ON UPDATE` on `updated_at`) to **`tags`** and
  **`scheduled_deletions`**. 3.0 reads both columns in every SELECT built from a model, so without
  them every tag lookup (every upload with tags) and every scheduled-deletion query fails.
  Additive, small tables. Harmless to 1.3.0 code.
- `database.sql` (fresh installs): same columns; `_magrathea_users.last_login` → `DATETIME NULL`
  (3.0's admin schema; a bare `timestamp` can get `ON UPDATE CURRENT_TIMESTAMP` on MySQL 5.7).

### Config, docs, scripts
- Removed the ignored `time_zone` key from `[general]` (`magrathea.conf`, `.sample`) (2.4.0 #33).
- `api/version`, `docs/openapi.yaml` → 1.4.0; `api/changelog.md` 1.4.0 entry (user-facing items as
  `improvement`/`fix` so the `/changelog` endpoint shows them; operator notes as `breaking`/`db`/
  `upgrade`).
- `docs/deploy.md`: new "Upgrading to 1.4.0 (MagratheaPHP 3)" section (§5).
- `scripts/deploy.sh`: "Create runtime directories" also creates the backups folder
  (`backups_path`, default `api/backups`), which 3.0's `check` warns about.
- `README.md`: MagratheaPHP 3; tree no longer lists `magrathea_objects.conf`.

## 4. Verified (local Docker stack as staging)

The local DB was empty (no prior containers on this machine), so `database.sql` was loaded fresh,
seeded with a test key / folder / file / share through the 2.x API, and snapshotted.

- `vendor/bin/magrathea check`: 0 errors. `models:verify`: 0 errors.
- 20 GET/error endpoints, before vs after: identical except
  - `version` (3.0.0), unknown route 200 → **404** (expected, 2.4.0 #16);
  - every `created_at` **3 hours earlier** (`06:22` → `03:22`): the timezone sync. Local MySQL is
    UTC, PHP is `America/Sao_Paulo`. 2.x was inconsistent: create responses carried PHP's local
    time, reads carried MySQL's UTC. 3.0 makes reads local. Legacy rows of the PHP-written
    `TIMESTAMP` columns `scheduled_deletions.requested_at`/`cancelled_at` will read 3h early;
    `DATETIME` columns (`expiration`, `execute_at`, `last_viewed_at`) are unaffected, and so are
    all PHP-side date comparisons (they compare `now()` with `DATETIME`s).
- Writes: create folder/share and upload with tags return `created_at`; rename keeps `created_at`
  and moves `updated_at` (`ON UPDATE` works); deletes, folder-not-empty, public share OK.
- `cron.php --dry-run` OK; usage error exits 1. `/app/` shell renders the app name.
- Admin: first-run page with no users; logged in (throwaway user); all 7 custom features render
  clean; GET to `Save` → 405 and no key created; POST with CSRF creates; POST without CSRF refused.
- `php -l` on every changed file; logs show only expected `MagratheaApiException`s.
- Base merge + strict types (follow-up), same stack. Baseline taken first, then after each
  feature and after dropping the pins:
  - the 20 GET/error endpoints above: byte-identical (masking only the `error-codes` cache flag
    and the share view counter the snapshot itself bumps);
  - a 41-step write-path run on a throwaway key, normalized and diffed: folders (create, dup name,
    rename, non-empty delete), uploads (text, PNG through the image pipeline, root + `no_convert`),
    tags attach/detach, file rename/delete, shares (file, folder, both → 4001, public file/folder/
    subfolder, delete), usage counters, key delete → 4014 on upload → cancel, then schedule +
    backdate + `cron.php --run` cascade (key, files, folders, shares, deletions all gone):
    identical every time;
  - admin, with strict types: all 7 custom pages render with fixture data, and every POST action
    works (key create/deactivate/reactivate, duplicate purge, share delete, browser file/folder
    delete, scheduled-deletion cancel + force-execute, GET to `Save` → 405): 29/29;
  - `ImportPipeline::Run` on a 3-level tree: 3 files, 3 folders, counters right;
  - `check` / `models:verify` clean; `php -l`; logs show only expected `MagratheaApiException`s.
- Composer, reproduced in a scratch project: with a lock pinning `magratheaphp2`,
  `composer install` exits 4 ("Required package platypustechnology/magratheaphp is not present in
  the lock file"); the targeted `composer update` in §5 fixes it, and plain `install` works after.

## 5. Production rollout (per instance) — pending

`composer.lock` is gitignored, so **every instance's own lock still pins `magratheaphp2`** and the
usual `git pull` + `composer install` fails, leaving new code on the old framework (down).

1. DB backup.
2. `git pull --ff-only`. If it refuses because of local edits to `api/src/setup.php`:
   `git checkout -- api/src/setup.php`, pull again (1.4.0 deletes the file).
3. Once, instead of `composer install`:
   `(cd api && composer update --no-dev --optimize-autoloader platypustechnology/magratheaphp platypustechnology/magratheaphp2)`
4. `mysql -u explorer -p magrathea_explorer < api/database/migrations/1.4.0_magrathea3.sql`
   (can also run before step 2).
5. `cd api && vendor/bin/magrathea check && vendor/bin/magrathea models:verify` — no ERROR.
   Create `api/backups/` if `check` warns.
6. Optional: `SELECT @@global.time_zone, @@system_time_zone;` — if MySQL isn't already at −03:00,
   timestamps in the app shift to local time (§4). Expected; `db_sync_timezone = false` reverts.
7. Every admin logs in again.

**Until an instance is upgraded, delete its `api/src/setup.php`:** on 2.3 the wizard has no lock
(it arrived in 2.4.0), so `/setup.php` is an open 2.x wizard with its `run-query`/`user-reset`/
`save-config` actions.
